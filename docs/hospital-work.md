# 서비스 업무관리: IndexedDB → Deno KV → Sheets

## Flow 엑셀 이전

`flow-import.html`은 Lv.3 관리자만 사용하는 2026년 이전 도구다. 로컬 엑셀에서 준비한 JSON을 선택해 병원 기준·기존 접수·이전 원본을 먼저 대조한다. 등록일시는 방문일시와 동일하게 저장하고, 작성자는 CS 담당 및 등록자, 담당자는 엔지니어로 보존한다. 요청사항은 구분으로, 상세내용만 접수 증상으로 사용한다. 정기점검은 점검으로, 업그레이드·업데이트·UI 작업은 A/S로 정규화한다. 원문과 처리 결과는 이력에 보존한다.

상태가 완료인 과거 내역은 완료를 유지한다. 기존 접수와 병원·방문일시가 일치하면 기존 접수의 상태·담당자·접수 내용은 유지하고 Flow 원문만 이력에 추가한다. 같은 날짜의 다른 방문 시각은 사용자가 기존 접수 추가 또는 별도 등록을 선택한다. 병원 기준이 명확하지 않으면 원본 병원명과 S/N의 별도 기준을 보존하며, 이후 기준 갱신에서도 삭제하지 않는다.

행 내용과 반복 순번으로 원본 ID를 만들고 원자적으로 이전 표식을 저장한다. 같은 파일을 다시 실행해도 접수·이력을 중복 생성하거나 휴지통 항목을 복구하지 않는다. 실패하면 다음 배치를 멈추며 동일 파일 미리보기에서 반영된 건을 건너뛰어 이어갈 수 있다. 과거 데이터를 공개 저장소에 포함하지 않는다. 시트 연동은 20건 배치를 최대 5회, 120초 이내로 처리하고 완료 건의 Handover 재조회는 제외한다.

고객센터가 병원 정보·접수 증상·담당자·방문 일시를 등록한다. 현장 보고는 기존 Handover에서 작성한다. A/S와 점검 결과를 접수에 연결하고 고객센터가 확인·완료한다. 댓글과 수정 이력은 접수별로 보관한다.

## 저장과 동기화

- IndexedDB는 사용자별 이 PC의 목록·병원 기준 정보·조회한 상세·미확인 저장을 보관한다.
- 보관 데이터가 있으면 접속 시 업무 서버를 조회하지 않는다. 첫 PC만 초기 목록을 가져온다.
- 다른 PC의 변경은 상단 **동기화** 버튼으로 가져온다. 변경 순번으로 최대 100건씩 받고 삭제 표시도 전달한다. 초기 목록은 200건씩 나눈다.
- 접수·댓글·처리 결과·완료·삭제·복원은 즉시 Deno KV에 저장한다. 저장 응답으로 화면을 갱신하므로 추가 상세 조회나 시트 반영을 기다리지 않는다.
- 모호한 저장 응답은 같은 operationId와 입력으로 재시도한다. 서버는 기존 응답을 반환한다. GAS로 쓰기를 우회하지 않는다.
- KV 확정은 완료됐으나 Sheets 반영은 대기 중일 수 있다. 하나의 원자적 저장에 접수·이력·감사 로그·변경분·시트 반영 대기를 포함한다.
- 5분 GAS 트리거가 최대 20건씩 시트에 반영한다. 버전 확인 후 eventId를 기록하고 KV에 해당 버전만 확인 응답한다. 실패하거나 응답이 유실되면 다음 실행에서 재시도한다.

IndexedDB나 HTML 파일은 공동 원본이 아니다. 브라우저 보관을 지워도 확정한 서버 기록은 유지된다. 저장되지 않은 초안은 해당 브라우저에만 있다.

## Handover 연결

병원명과 **방문 날짜 = 처리 날짜**로 비교한다. 방문 시간은 매칭에 포함하지 않는다. 날짜 표기 `2026. 10. 6`은 `2026-10-06`으로 정규화한다. A/S와 점검 모두 대상이다.

같은 병원·날짜에 접수와 원본이 각각 하나이고 결과가 있으며 장비 S/N이 충돌하지 않을 때 자동 연결한다. 여러 접수나 여러 원본, S/N 불일치, 결과 미기록은 자동 연결하지 않는다. 상세의 **Handover 결과 불러오기**에서 직접 비교·선택한다. 삭제되지 않은 다른 접수에 연결한 원본은 재사용하지 않는다. 연결된 접수가 휴지통에 있으면 같은 원본을 새 접수에 자동 또는 수동으로 연결할 수 있다. 기존 휴지통의 접수·결과·보완 메모·수정 이력과 Handover 원본은 보존하고, 새 접수에는 별도 결과 이력을 만든다. 이미 남아 있는 휴지통 연결 정보도 새 연결 시 소유 접수의 삭제 여부를 확인하므로 별도 데이터 초기화가 필요하지 않다.

새 접수로 연결한 뒤 기존 접수를 복원해도 새 연결을 빼앗지 않는다. 원본 연결 정보와 이전 소유 접수의 버전을 함께 확인하여, 복원과 재연결이 동시에 일어나거나 두 접수가 동일 원본을 선택해도 삭제되지 않은 한 접수만 연결을 차지한다. 이전 소유 접수를 찾지 못하면 삭제로 추정하지 않고 기존 연결을 보호한다.

새 자동 연결은 **결과확인**으로 두고 고객센터가 완료한다. 이전 완료 상태·접수 담당자·예정 일정은 보존한다. 처리 구분 A/S·점검은 실제 연결된 원본을 기준으로 상세 상태 옆에 표시한다.

Handover 저장 훅은 시트의 durable 대기에 기록한다. 5분 작업은 누락된 저장 훅도 접수의 병원·날짜로 다시 확인한다. 원본 조회 버튼은 GAS에서 최신 원본을 가져와 KV에 전달한다. 시트 반영 전의 새 접수도 KV가 확인한 병원명으로 원본 조회가 가능하다. 원본에 기록 ID가 없으면 잠금 아래 UUID를 붙인다.

## 삭제와 충돌

등록자 또는 Lv.3 관리자가 선택한 **접수 한 건**을 휴지통으로 이동·복원한다. 댓글·처리 결과·수정 이력·Handover 원본·병원 기준 정보는 보존한다. 영구 삭제 API는 없다.

평소에는 목록의 체크박스와 선택 도구를 숨긴다. 상태 드롭다운 아래 **삭제**를 누르면 행·휴대폰 카드의 체크박스가 활성화되고, 접수를 체크한 뒤 **선택 삭제**를 누른다. **삭제 모드 닫기**는 선택을 모두 해제한다. **현재 페이지 전체 선택**은 화면에 표시된 최대 50건 중 관리 권한이 있는 접수만 선택한다. 검색·정렬·페이지를 변경하면 선택을 해제하고, 빠른 필터 변경은 선택 모드도 닫는다. 확인 창에 병원·방문 일정·상태·증상을 표시한 뒤 휴지통으로 이동한다. 휴지통 목록에서는 같은 위치의 **복원**으로 체크박스를 열고 **선택 복원**을 사용한다.

접수 창의 등록일과 방문·처리일은 날짜 달력과 직접 입력하는 시간 칸으로 나눈다. 시간은 `10:00`, `1000`, `930` 형태를 24시간 기준으로 정규화하며, 잘못된 시간이나 날짜 없는 시간은 저장하지 않는다. 초안은 입력 중인 값을 보존한다. 새 접수의 업무 마감 입력은 제외하고, 기존 접수를 수정할 때 저장된 마감 값은 보존한다. API의 `registeredAt`·`visitAt` 저장 형식은 기존과 같다.

여러 접수는 기존 API로 한 건씩 저장한다. 성공한 접수만 목록에서 빠지며, 실패·충돌한 접수의 선택은 유지된다. 저장 결과가 불확실하면 다음 건 처리를 중단하고 기존 저장 식별자로 결과를 재확인한다. 오래된 버전을 강제로 덮어쓰지 않는다.

오래된 PC의 수정은 baseRevision으로 막는다. 댓글 추가끼리는 보존하고 같은 댓글 수정끼리는 이력 버전을 비교한다. 삭제된 접수에는 댓글이나 결과를 추가할 수 없다. 복원 시 미완료 요청·담당자의 동일 방문 일정이 겹치면 확인이 필요하다.

## 구성과 배포

- Deno: `deno-auth/main.ts` + `deno-auth/work-store.ts`.
- 웹: `hospital-work.html`, `js/baz-work-cache.js`, `js/baz-work-api.js`, `js/baz-work-manager.js`, CSS와 SW.
- 기존 Handover GAS 프로젝트: `hospital_work_gas.gs` 교체 + `hospital_work_kv_gas.gs` 추가.
- 운영 Code.gs는 유지한다. 기존 work_* 라우팅과 hospitalWorkHandoverSaved_ 훅을 사용한다.
- 기존 Deno KV의 `hospitalwork-v2` 이름 공간을 사용한다. 로그인·사용자·기기 데이터와 환경변수는 유지한다.
- 기존 WORK_API_ENABLED, WORK_GAS_URL, TOKEN_SECRET 설정을 사용한다. 새 공개 토큰이나 클라이언트용 비밀키를 추가하지 않는다.
- GAS bazTokenConf_().secret과 Deno TOKEN_SECRET은 기존 세션 서명에 쓰던 동일한 설정이다. 서버 bridge는 별도 서명 문맥과 5분 유효시간·nonce 중복 방지를 사용한다.

배포 순서:

1. 호환 Deno 빌드를 배포한다. KV 준비 전에는 기존 GAS 경로를 유지한다.
2. 두 업무 GAS 모듈을 적용하고 기존 웹 앱 배포를 새 버전으로 갱신한다. URL은 유지한다.
3. GAS 편집기에서 `migrateHospitalWorkToKv`를 실행한다.
4. 기존 GAS 미완료 저널을 복구하고 업무 쓰기를 동결한다. 기존 네 업무 탭을 timestamp 백업으로 복사한다.
5. 접수·이력·확정된 operationId/응답을 기존 ID·시각·버전 그대로 KV에 옮긴다. 병원 원본과 권한·담당자 기준 정보를 전달한다.
6. 접수·이력·operation 전체의 건수와 SHA-256을 양쪽에서 비교한다. 일치한 경우에만 KV를 활성화한다.
7. GAS 단계는 active로 두고 `syncHospitalWorkKv` 5분 트리거를 생성한다. 실행이 중단되면 같은 함수 재실행으로 준비/활성화 후속 단계를 마칠 수 있다. 활성 KV에 시드를 다시 쓰지 않는다.
8. 새 웹 페이지에서 동기화·상세·댓글·삭제/복원·점검 매칭과 시트 반영을 확인한다.

추가 탭:

| 탭 | 용도 |
|---|---|
| 업무KV변경로그 | 시트에 반영된 KV eventId·순번·내용 |
| 업무Handover대기 | 원본 기록 ID·버전·전달 대기/완료 |
| 업무연동관리 | 검증 결과, 마지막 성공, 실행 시간, 오류와 반영 대기 |
| *_KV전환백업_날짜시간 | 이전 네 업무 탭의 변경하지 않은 사본 |

기존 업무요청·업무처리이력·업무병원은 KV의 시트 사본으로 유지한다. 이전 업무변경로그도 유지한다. 운영 시트에서 이 JSON을 직접 수정해도 KV 원본에는 반영되지 않는다. Handover 본문은 기존 방식으로 작성한다.

## 복구와 성능

시트 작업 실패는 KV 저장 결과를 되돌리지 않는다. 업무연동관리의 오류와 GAS 실행 기록을 확인한 후 worker를 재실행한다. 큐를 비우거나 활성화 플래그만 지우는 방식으로 되돌리지 않는다. GAS로 복귀해야 한다면 쓰기를 중지하고 KV의 모든 변경·삭제 표시와 감사 이력을 시트에 반영한 뒤 건수·내용을 확인하는 별도 복구가 필요하다.

접수/댓글 저장은 KV가 담당한다. Handover 최신 원본 조회는 GAS 경로이므로 3초 응답 대상과 구분한다. 첫 서버 기동이나 네트워크 지연까지 모든 요청의 3초 이내를 보장하지 않는다. UI는 목록 보관과 저장 후 재조회 제거로 지연을 줄인다. 1분 keep-warm이나 지속 polling은 사용하지 않는다.

모든 KV 값은 UTF-8 48KB 이하로 검사한다. 첨부 사진·영상은 저장하지 않는다. 요청과 로그를 페이지로 나누며 오래된 서버 기록의 자동 영구 삭제는 하지 않는다. 사용자 5명 × 하루 저장 20회·수동 동기화 10회 × 22일은 사용자 HTTP 요청 약 3,300회/월이며 인증·원본 조회·GAS worker·KV 읽기/쓰기 단위는 별도다.

## 검증

Node 24 이상에서 실제 저장 모듈과 GAS 테스트 fixture를 실행한다:

```sh
node test/work-kv.mjs
node test/work-bridge.mjs
node test/work-api-transport.mjs
node test/work-ui-cache.mjs
node test/hospital-work.mjs
node test/deno-auth-security.mjs
```

KV 테스트는 재시도·동시 댓글·버전 충돌·점검 자동 결과 확인·모호한 원본·삭제 표시 동기화·복원·정확한 큐 확인 응답·지연 원본 거부·활성화 검증을 다룬다. GAS 테스트는 기존 Handover 저장 회귀, KV 단계의 구식 쓰기 차단, 시트 반영 중단/재전달/낮은 버전 보호를 검증한다. UI 테스트는 보관 PC의 서버 요청 없는 시작과 버튼 동기화를 검증한다. 기존 인증 회귀도 유지한다.
