# 병원 A/S 업무관리 — 첫 구현 및 배포

고객센터가 병원·증상·CS 담당자·배정 엔지니어·방문 일시를 한 폼에서 등록한다. 구두 일정 협의 단계는 화면으로 만들지 않는다. 현장은 기존 Handover를 사용하며 병원명과 방문일이 저장된 A/S 원본의 병원명·처리일과 일치하고 업무와 원본이 각각 한 건이면 결과를 자동 연결하고 완료한다. 연결이 모호한 건은 고객센터가 원본을 직접 선택해 등록·완료한다. 요청 상세에 댓글, 결과 카드, 이전 내용과 변경 기록이 남는다.

## 포함한 범위

- `hospital-work.html` 독립 화면과 메인 메뉴 연결.
- PC 목록·상세, 모바일 카드·상세, 밝은/어두운 테마.
- 병원 원본 드롭다운, 연결 정보 자동 입력, 기존 처리 이력 조회.
- 방문 예정·처리중·결과확인·완료·보류·취소. 미정 접수에는 접수 상태.
- 중복 요청 안내와 기존 요청 열기, 같은 엔지니어의 **동일한 방문 일시** 경고. 방문 소요 시간·이동시간을 계산하는 일정 최적화는 포함하지 않는다.
- 댓글 추가/수정과 수정 전 내용 보존. 본인 댓글 또는 Lv.3 관리자만 수정.
- Handover의 처리일·실제 처리자·장비·유형·내용·결과·교체품·비용·비고 자동 입력. 고객센터 보완 메모는 원본과 구분.
- 결과 원본 ID·버전 검사, 재불러오기와 저장 재시도 중복 방지, 완료 시각·처리자.
- 최초 1회 및 동기화 버튼 조회. 상세 조회와 결과 불러오기는 사용자 행동에 따른 조회다. 자동 폴링·포커스 복귀 동기화는 없다.
- 초안과 결과 불명 저장 요청은 사용자 이름별 브라우저 키로 보존한다. 공유 원본은 시트다.

외부 알림, 사진·영상 복제, 간트차트, 백업/복원 UI는 첫 구현에서 제외했다. Handover 입력 화면은 유지한다. 병원명·방문일의 유일한 일치는 자동 연결하고, 중복이나 확인이 필요한 건은 고객센터가 직접 선택한다. 업무 번호를 Handover로 전달하는 명시적 연결은 후속 확장이다.

## GAS 준비 — 같은 handover 프로젝트

1. 기존 handover 스프레드시트의 Apps Script 프로젝트를 연다. 실제 `Handover.gs`가 이 저장소의 `handover_gas.gs`와 대응하는지 확인한다. 기존 편집 내용이 있으면 먼저 비교·보존한다.
2. 저장소의 `handover_gas.gs` 변경은 `doGet/doPost`의 `work_*` 라우팅과 원본 저장 성공 후 `hospitalWorkHandoverSaved_` 호출이다. 기존 코드에 해당 변경을 적용한다. 별도 doGet/doPost를 추가하지 않는다.
3. `hospital_work_gas.gs`를 같은 프로젝트에 새 스크립트 파일로 추가한다. 서명 토큰 이름 검증을 위해 기존 `baz_token_lib.gs`와 동일한 인증 설정이 있어야 한다.
4. 스프레드시트에 연결된 편집기에서 `setupHospitalWork()`를 실행한다. 기존 현장 처리 탭 존재를 확인한 뒤 `업무요청`, `업무처리이력`, `업무변경로그`, `업무병원`을 만들고 `HOSPITAL_WORK_SS_ID` 스크립트 속성에 파일 ID를 저장한다. 재실행은 기존 데이터나 탭을 지우지 않는다. 다른 헤더가 있으면 중단한다.
5. 같은 웹앱 배포를 새 버전으로 갱신해 URL을 유지한다. 다른 URL을 사용하면 `js/baz-work-api.js`의 URL도 실제 URL로 변경한다.
6. 기존 병원 원본 조회·엔지니어 원본 목록이 정상인지 실제 계정으로 확인한다. CS 담당자는 로그인 이름을 기본값으로 하고 이전 접수 담당자를 자동완성 후보로 제공한다. 엔지니어 후보를 CS 명단으로 사용하지 않는다.
7. HTML 변경을 배포한다. 서비스워커 버전은 v184다. `메뉴설정`에 `hospitalwork`를 등록해 표시·접근 등급·순서를 운영 대상에 맞게 조정한다. 기본 등급은 기존 Handover와 같은 **1**이며 서버도 이 메뉴 등급을 검사한다. 더 높은 등급을 설정하면 현장 계정 접근도 함께 제한된다.

현재 작업에서는 실제 Apps Script 프로젝트·시트 편집 권한을 사용하지 않았으며 웹앱 배포, 실제 공유 저장·응답 시간은 확인하지 않았다. 로컬 테스트의 인증·시트·통신은 검증용 대체 환경이다.

## 저장·이력 보존

`업무변경로그`의 단일 준비 행에 operationId, 서버 확인 작성자, 페이로드 지문, 이전/이후 값, 최초 응답을 기록한다. 요청·댓글 시트에 반영한 뒤 커밋 표시를 한다. 시트 반영이 중단되면 다음 읽기 또는 쓰기에서 ScriptLock 안에서 준비 기록을 재반영하고 커밋한다. 모든 새 쓰기는 복구 후 진행한다. 같은 operationId의 같은 내용은 최초 응답을 반환하고 다른 내용은 거부한다. 로그는 복구와 중복 방지의 원본이므로 수동으로 지우거나 정렬·열 구조를 바꾸지 않는다.

여러 PC의 요청 수정은 revision으로 비교한다. 충돌 화면은 서버 값과 입력 값을 보여주며 본인이 변경한 필드만 최신 값 위에 유지하거나 서버 내용으로 다시 시작할 수 있다. 댓글 수정과 결과 갱신에도 각각 버전 검사를 적용한다. 저장 중 입력을 잠시 비활성화하여 전송 도중 수정한 내용이 성공 응답으로 지워지는 것을 방지한다.

Handover 원본은 정확한 병원명과 기록 ID로 조회한다. 기존 recent API의 부분 일치·누락 필드를 사용하지 않는다. 기록 ID가 없는 과거 건은 수동 선택 또는 유일한 자동 일치 행의 내용 지문을 확인한 뒤 원본의 `기록 ID` 열에 UUID를 부여한다. 이 경우에만 원본의 ID 열을 추가하거나 빈 ID를 채우며 보고서 본문은 수정하지 않는다. 행 번호는 영구 식별자로 저장하지 않는다. 같은 원본 결과를 다른 요청에 중복 연결하면 거부한다.

원본 처리 담당자를 새 업무의 CS 담당자에 덮어쓰지 않으며 처리일도 계획 방문 일시와 구분한다. 결과 원본에 없는 값은 미기록으로 표시한다. 원본 수정은 결과 카드의 ‘원본 비교·갱신’으로 비교 후 저장하고 고객센터 메모·완료 상태를 보존한다. 병원명·방문일이 유일하게 일치하는 저장된 A/S 결과는 자동 연결·완료한다.

## 검증

```text
node test/hospital-work.mjs
node test/handover-integrity.mjs
node test/gas-sync-p0.mjs
node test/browser/hospital-work.cjs
```

브라우저 테스트는 기존 Playwright와 Edge를 사용한다. 모듈 경로가 표준 위치가 아니면 `PLAYWRIGHT_MODULE`, 브라우저 채널은 `BROWSER_CHANNEL`로 지정할 수 있다. `HOSPITAL_WORK_SCREENSHOTS`에 캡처 출력 경로를 지정한다. 실제 서버에 테스트 데이터를 쓰지 않는다.

GAS 테스트는 실제 업무 모듈과 기존 GAS 함수를 실행해 인증, 병원/담당 원본 검사, 중복 안내, revision 충돌, 댓글 권한/수정, 정확한 결과 항목 매핑, 원본 변경 검사, 과거 기록 ID, 부분 저장 복구를 확인한다. 브라우저 테스트는 실제 화면 코드를 대상으로 접수·댓글 수정 초안·충돌 병합·결과 완료·응답 불명 후 새로고침/재시도·수동 동기화·PC/모바일/다크모드를 확인한다.

첫 버전은 목록·이력·변경로그를 시트에서 일괄 읽고 화면 목록을 50건씩 표시한다. 화면 페이지 분할이 서버 읽기 비용을 줄이는 구조는 아니다. 대량 데이터 성능·보관 정책은 아직 검증하지 않았으므로 실제 업무량과 동시 사용자 수로 최초 조회·상세·저장 지연을 측정한 뒤 서버 조회 범위/색인·기간별 보관을 확장한다. 데이터 자동 삭제나 날짜별 초기화는 없다.

## 상세 화면 표시 개선

병원 클릭 시 목록에 있는 접수 정보를 먼저 표시하고, 댓글·처리 결과·변경 이력은 `work_detail` 응답 후 표시한다. 처음 조회 중인 댓글 수는 0건 대신 ‘확인 중’으로 표시한다. 최근 상세 최대 20건은 현재 탭 메모리에서만 보존하며 재방문 시 이전 내용임을 표시하고 서버에서 다시 확인한다. 최신 확인 중이거나 조회에 실패하면 기본 정보 수정·결과 등록·완료·댓글 저장을 비활성화한다. 댓글 초안은 그대로 보존하고, 실패 시 상세 화면의 ‘최신 내용 확인’으로 재시도할 수 있다.

같은 상세 조회 중의 연속 클릭은 중복 요청을 보내지 않는다. 병원을 전환하거나 상세를 닫은 후 도착한 이전 조회 성공·실패는 현재 화면을 바꾸지 않는다. 모바일에서는 클릭 즉시 상세 위치로 이동하며 응답 도착 때 다시 스크롤하지 않는다. 상세 화면 즉시 표시 자체는 프런트엔드 개선이며 서버 응답 시간 단축을 의미하지 않는다. 아래 자동 연결 기능을 함께 적용하려면 GAS 모듈 두 파일을 갱신하고 기존 웹앱을 새 버전으로 배포해야 한다.


## 방문일 기준 Handover 자동 연결·완료

- 비교 기준은 병원명의 양끝 공백을 제거한 정확한 이름과 병원 업무의 `visitAt` 날짜(한국 시간) ↔ Handover `처리일`이다. 접수 등록일은 비교하지 않고 날짜의 시각은 제외한다. 부분 일치·분점 추정은 하지 않는다.
- Handover의 행과 사진 저장이 확정된 후 기존 ScriptLock 안에서 자동 연결한다. 모듈 미설치 또는 미초기화 상태는 기존 Handover 저장을 유지한다. 보조 작업 실패도 원본 저장 성공을 유지하고 다음 업무 조회에서 저널을 복구한다.
- 최초 조회·수동 동기화·상세 조회에서도 자동 일치를 확인하므로 이미 저장된 원본이나 저장 훅 실패를 다시 처리한다. 조회 API가 이 조건에서 업무 결과·완료를 기록할 수 있다. 브라우저 자동 폴링이나 별도 외부 전송은 추가하지 않는다.
- 자동 대상은 방문 날짜가 있는 접수·방문예정·처리중·결과확인 업무다. 완료·보류·취소는 자동으로 변경하지 않는다. 동일 병원·날짜의 업무 수는 취소를 제외한 완료·보류도 포함해 중복 연결을 방지한다.
- 동일 병원·날짜의 A/S 원본이 한 건이어야 하며 일반 점검 기록은 대상이 아니다. 처리 결과 미기록, 양쪽 S/N 불일치, 중복 기록 ID, 다른 업무에 이미 연결된 원본, 기존에 다른 결과를 선택한 업무는 자동 완료하지 않고 상세에 수동 확인 사유를 표시한다.
- 자동 완료 후 사용자가 다시 연 업무는 이전 자동 결과로 재완료하지 않는다. 새 처리 결과를 확인하고 수동으로 연결·완료한다.
- 결과에 실제 처리자·처리일·장비·유형·처리 내용·결과·교체품·비용·비고를 보존한다. CS 담당자와 예정 방문 일시는 유지한다. 이미 같은 원본을 선택한 결과확인 업무는 고객센터 메모와 결과 카드 ID를 보존한다.
- 자동 이벤트는 `result_auto`, 처리자는 `Handover 자동 연결`로 감사 기록에 남고 결과 카드에는 자동 연결 표시가 붙는다. 원본 ID·버전·업무 revision으로 만든 operationId와 기존 prepared/committed 저널을 사용해 중복과 부분 저장을 방지한다. 과거 원본에 ID가 없으면 해당 ID 셀만 채운다.
- 자동 일치 확인은 Handover 전체 보고서를 전달받지 않고 병원명·처리일 열과 일치 행만 읽는다. 실제 운영량의 속도와 동시 저장 지연은 배포 후 확인해야 한다.

배포: `handover_gas.gs`의 저장 성공 훅과 `hospital_work_gas.gs`를 같은 GAS 프로젝트에 함께 반영하고 기존 웹앱을 새 버전으로 배포한다. PR #195에서 setup을 마쳤으면 전용 시트 재생성이나 DB 이전은 필요하지 않다. 백엔드를 먼저 갱신한 뒤 정적 페이지를 적용한다.
