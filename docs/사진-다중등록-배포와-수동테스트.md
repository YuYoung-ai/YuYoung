# 다중 사진 등록 — 배포 절차와 수동 테스트

GAS v3.4.0 / 서비스워커 `baz-cs-v133` 기준. 이 저장소에는 Apps Script 자동 배포(`.clasp.json`)가 없으므로 **서버는 편집기에서 수동 배포**해야 한다. 브랜치 병합·Pages 배포만으로 GAS 가 반영되지 않는다.

---

## 1. 배포 순서

### 1-1. 서버 (Apps Script 편집기)

1. **백업** — 현재 `handover_gas.gs` 전문을 로컬 파일로 저장한다.
2. 새 `handover_gas.gs` 를 붙여넣는다.
3. **배포 → 배포 관리 → ✏️ → 버전: 새 버전 → 배포** (URL 유지. "새 배포"가 아니다)
4. 확인: `배포URL + ?action=ping` → `{"success":true,"ver":"3.4.0"}`

### 1-2. 초기 설정 (편집기 Run)

시트 생성과 백필은 **분리돼 있다**. 한 번에 다 하면 6분 실행 한도에 걸린다.

```
setupPhotoSheet()
```
- `현장 사진` 시트 생성(헤더 11열 + 고정 행 + 텍스트 서식)
- 메인 시트에 **`기록 ID` 열 1개** 생성 (마지막 헤더 오른쪽)
- Drive 권한 승인 창이 뜨면 승인한다

```
backfillLegacyPhotos(200)
```
- 기존 행에 영구 legacy 기록 ID(`LEGACY-{행}-{파일ID앞8자}`) 부여
- 기존 S/N 사진을 `현장 사진` 시트에 `SN` 구분으로 등록
- **잔여가 0 이 될 때까지 반복 실행한다.** 커서가 ScriptProperties(`snap_backfill_row`)에 남아 이어서 진행된다
- 멱등: 이미 기록 ID 가 있거나 같은 Drive 파일 ID 가 등록돼 있으면 건너뛴다

```
getPhotoMigrationStatus()
```
- `{total, done, remain, cursor, photoRows, hasRecordIdCol, hasPhotoSheet}` 로 진행 확인
- `remain: 0` 이면 백필 완료

### 1-3. 프론트

브랜치를 push 하면 Pages 가 배포한다. `sw.js` 의 `CACHE_VERSION` 은 이미 `baz-cs-v133` 으로 올려 두었다.

### 1-4. 정기 정리 (선택)

```
cleanupOrphanPhotos(48)
```
기록에 끝내 연결되지 않은 `ORPHAN` 사진과 Drive 파일을 정리한다. 48시간 이상 지난 것만 지우며 `OK`(연결 완료)는 건드리지 않는다. 시간 기반 트리거를 걸어도 되고 필요할 때 수동 실행해도 된다.

## 2. 수동 테스트 (실제 GAS·Drive 연결 필요)

자동 테스트(`node test/photo-multi.mjs`)는 시트·Drive 를 mock 으로 대체한다. 아래는 **실제 연결에서만 확인 가능한 항목**이다.

### 2-1. 설정 확인

| # | 절차 | 기대 |
|---|---|---|
| 1 | `setupPhotoSheet()` 실행 | `현장 사진` 시트 생성, 메인 시트 마지막에 `기록 ID` 열 추가 |
| 2 | 다시 실행 | 중복 생성 없음, "기록 ID 열 이미 있음" |
| 3 | `backfillLegacyPhotos(50)` 반복 | `remain` 이 줄어들고 0 에서 멈춤 |
| 4 | 백필 후 메인 시트 확인 | 모든 기존 행에 `LEGACY-...` 기록 ID |
| 5 | 백필 후 행 정렬 변경 | 기록 ID 가 따라 움직이고 사진 연결이 유지됨 |
| 6 | `backfillLegacyPhotos` 재실행 | 같은 사진이 두 번 등록되지 않음 |

### 2-2. 업로드

| # | 절차 | 기대 |

| 7 | S/N 사진만 첨부 후 저장 | 기존과 동일하게 저장, 시트 사진 열에 `=IMAGE()` |

## 3. 자동으로 검증하지 못한 항목

- **Drive 썸네일 대리 조회의 실제 동작** — `UrlFetchApp` 이 `drive.google.com/thumbnail` 에서 이미지 바이트를 받아오는지는 배포 후에만 확인 가능하다. 실패해도 원본 blob 폴백이 있어 기능은 유지되나 **속도 개선은 없다**. 위 2-3 #22 로 확인한다.
- 실제 Drive 파일 생성·공유 설정·휴지통 이동
- 시트 쓰기 동시성(실제 LockService 경합)
- 백필 대상 행 수와 6분 한도 도달 여부
- 실제 카메라 촬영본(HEIC 등)의 압축 결과와 용량

## 4. 보안 주의 (사용자 결정에 따른 트레이드오프)

사진은 `savePhoto_` 가 **`ANYONE_WITH_LINK`** 로 공유한다. 시트 `=IMAGE()` 렌더링과 썸네일 대리 조회에 필요하며, 안정성·속도를 우선한 의도적 선택이다.

**링크를 아는 사람은 누구나 사진을 열람할 수 있다.** S/N 라벨과 달리 **문제 원인 사진에는 병원 내부·환자 주변 환경이 함께 찍힐 수 있으므로**, 화면에 촬영 범위를 좁히라는 안내를 두었다. 링크가 외부로 유출되지 않도록 Excel·PPT 파일 공유 범위를 관리해야 한다.

비공개 전환(공유 해제 + OAuth 프록시 전용)은 이번 범위에 포함하지 않았다. 필요해지면 `SNAP` 주석의 트레이드오프 설명을 참고해 후속 작업으로 진행한다.

그럼에도 다음은 유지된다.

- 인증(`requireWrite_`) 없는 사진 업로드 차단
- **최종 저장 payload 에서 Drive 파일 ID 를 아예 받지 않음** — 서버가 `recordId+clientPhotoId` 로 결정
- 조작된 `clientPhotoId`·타인의 `recordId` 사진 연결 거부
- 파일명(`safeName_`)·설명(`safeCell_`) 정리로 수식 주입 방어
- 같은 `clientPhotoId` 재전송 시 Drive 중복 파일 방지
