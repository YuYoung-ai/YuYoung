# 앱 Handover 검수 도입을 위한 동기화·잠금 안정화 실행계획

수정일: 2026-10-15 (한국시간)

검토 기준: main `f4429af2b143ed0ab83f10c790d731bb02ddd5f8` / PR #246

상태: 관리자 1명·편집 잠금 없음 기준의 최종 기술 부속 계획. 기능 변경·운영 변경·배포는 수행하지 않았다. 작업 시작 지침은 [Codex 구현 인계서](codex-handover-implementation-handoff.md)를 따른다.

## 1. 이 문서의 역할

업무 설계 기준은 [기존 앱 수정모드 기반 Handover 검수·저장·공유 최종 계획서](handover-review-publish-plan.md)이다. 이 문서는 그 설계를 위한 동기화·잠금·원본 수신·복구 기술 기준만 다룬다.

지정된 관리자 1명만 기존 앱 수정모드에서 Handover 본문을 검수하고 Deno에 저장한다. 일반 사용자는 신규 작성·최초 저장 후 본문을 수정하지 않는다. 편집 중 데이터는 브라우저 초안이며 공유 조회에는 기존 저장본을 제공한다. 저장 성공 시 전체 새 본문과 버전을 원자적으로 확정한다.

앱 편집 잠금·점유 예약·잠금 만료 기능은 도입하지 않는다. 동일 관리자의 두 창/기기 충돌은 저장 순간의 버전 검사로 방지한다. 아래 GAS 저장 잠금과 서버 작업 중복 실행 제어는 편집 잠금과 다른 목적이다. 별도의 시트 검수·수동 전송 절차를 두지 않는다. PDF는 현장 생성 당시 내용으로 고정하고 검수·원본 정정과 독립적으로 즉시 생성·저장·공유·첨부한다.

## 3. 순수 목록 조회

- 일반 목록 동기화는 KV 변경분과 필요한 기준정보만 조회한다. GAS 원본 대조·수신·자동 연결을 실행하지 않는다.
- 최초 접속의 계정별 캐시와 `work_bootstrap` 페이지 로딩은 유지한다. 명시적인 최신 상세 조회·저장 결과 확인은 강한 일관성 읽기 또는 동등한 버전 검증을 사용한다. 캐시 표시는 최신 서버 조회 완료와 구분한다.
- 변경분은 시작 상한 seq를 고정하고 모든 페이지에 적용한다. 새 변경은 다음 조회에서 받는다.
- 페이지는 임시 Map에 병합하고 최종 성공 시 데이터와 revision을 함께 확정한다. 중간 실패는 마지막 정상 revision으로 재개한다.
- 커서가 전진하지 않는 응답은 무한 반복하지 않고 중단·진단한다.
- 구조화된 `REVISION_INVALID`만 1회 전체 재조회로 복구한다. 인증·일반 네트워크 오류를 전체 조회로 바꾸지 않는다.
- 늦은 목록 응답이 높은 revision의 검수 저장 결과·초안을 덮어쓰지 못하게 한다.
- 반복 페이지마다 병원 기준정보·근무일정을 모두 보내는 비용은 측정 후 줄인다. 생략 필드는 기존 값을 유지한다.

기존 API 응답 형식을 호환 유지한다. 순수 조회로 전환하기 전에 신규 접수·조건 변경·복원·원본 수신의 자동 연결 대기 처리를 준비한다.

## 4. 원본·검수·문서·보고 이벤트 분리

| 경로 | 책임 | 다른 경로에 미치는 제한 |
|---|---|---|
| 현장 원본 수신 | 최초 저장 스냅샷 보관·필요한 매칭 대기 | 기존 본문 재수정 차단, 비정상 변경 격리, 검수본 덮어쓰기 금지 |
| 관리자 앱 저장 | 본문 버전 CAS·검수본·감사·변경분·반영 이벤트 원자적 확정 | 편집 잠금 없음, 초안 미노출, GAS 통신을 기다리지 않음 |
| PDF 전달 | 문서 파일/메타데이터·접수 첨부 | 검수 승인·원본 최신 지문 불일치를 요구하지 않음 |
| GAS/보고 반영 | 검수 버전별 복제와 공통 조회 계층 적용 | 신규 현장 원본으로 재수신하는 순환 금지 |
| 목록/알림 조회 | 서버의 공유 검수본 조회·열람 확인 | 원본 수신·검수 저장을 부수 효과로 실행하지 않음 |

일반 사용자의 최초 저장 재시도와 기존 기록 수정은 작업 ID·payload로 구분한다. 기존 recordId를 신규 작성 API로 덮어쓰지 못하게 한다. 기존 API·구버전 클라이언트·GAS 경로에도 지정 관리자 권한 정책을 적용한다. 관리자 여부는 인증된 계정 식별자와 서버 설정으로 검증한다. `verifyToken().uid`를 `workForward()`에서 저장소 Actor까지 전달하고 지정 계정 검증을 추가한다. uid 없는 구형 토큰은 본문 검수 저장에 한해 재로그인이 필요하다.

모든 기록은 불변 recordId로 식별한다. 병원명·행 번호만으로 변경 대상을 추정하지 않는다. 클라이언트가 주장하는 requestId/recordId 연결은 서버의 인증된 맥락과 현재 대상 상태로 검증한다.

## 5. GAS 잠금 축소

### 5.1 현장 저장 후처리

잠금 안에서 원본 저장과 내구성 있는 원본 수신 이벤트 기록을 확정한 뒤 잠금을 해제한다. Deno 통신·대기 집계 게시·긴 부가 작업은 밖으로 이동한다. 보조 작업 실패가 성공한 원본 저장·사진 업로드를 재실행하게 만들지 않는다.

현재 저장 함수의 `return json_(out)`/`finally` 경계를 고려해 저장 핵심 함수가 결과·후처리 항목을 반환하도록 책임을 나눈다. 이미 직렬화한 응답을 finally에서 수정하려 하지 않는다.

### 5.2 읽기와 짧은 쓰기 분리

- 긴 조회·비교·전송은 잠금 밖에서 한다.
- 안정 ID 할당·대기 이벤트 확정·처리 상태 갱신은 짧은 잠금으로 보호한다.
- 잠금 밖에서 읽은 행 번호·내용을 그대로 신뢰하지 않는다. 재획득 후 불변 ID·버전을 확인하고 바뀐 대상은 재대기한다.
- 여러 시트를 전역적으로 동일한 한순간에 읽었다고 표현하지 않는다. 잠금을 따르지 않는 직접 시트 수정도 버전 검증에 포함한다.
- 관리용 조회는 짧은 잠금 시도 후 `BUSY`를 반환한다. 초기 제안 0.5~1초는 운영 실측으로 조정한다. 실제 저장의 대기 정책과 구분한다.
- 잠금 대기 시간을 일괄 증가시키는 것을 해결책으로 삼지 않는다.

### 5.3 배치 처리

원본마다 대기열 전체를 다시 읽는 반복을 줄이고 배치 시작 시 필요한 인덱스를 구성한다. 기존 최대 20건을 초기 기준으로 삼되 처리 시간·바이트 예산을 함께 둔다. 현재 28초 GAS 중계 한도 안에 작은 요청이 끝나도록 한다.

Sheets의 여러 셀 갱신은 원자적 트랜잭션이 아니므로 준비·확정 저널과 동일 이벤트 재실행으로 부분 실패를 복구한다. 전송 확인 전 대기 이벤트를 지우지 않는다. Deno 수신/저장과 GAS 미러링의 성공 시점을 각각 기록한다.

## 6. 자동 연결의 누락 방지

| 이벤트 | 후속 처리 |
|---|---|
| 신규 접수 | 이미 수신된 원본과 매칭하도록 해당 접수 대기 기록 |
| 연결 조건 수정·복원 | 최신 접수 버전으로 대상 재검사 |
| 신규 원본 수신·누락 원본 복구 | 해당 병원·처리일 후보와 기존 ID 연결만 재검사. 기존 본문 변경은 자동 적용하지 않고 격리 |
| 관리자 검수 저장 | 검수본의 이력·요약·변경분·보고 반영 이벤트 생성 |
| PDF 수신 | 문서 연결만 처리. 관리자 검수본 확정으로 간주하지 않음 |

관련 데이터와 대기 항목은 가능한 범위에서 같은 KV 원자적 트랜잭션으로 확정한다. 처리기는 대상 revision을 검증하고 성공한 항목만 제거한다. 처리 도중 새로 갱신된 대기 항목을 이전 실행이 삭제하지 못하게 한다.

검수 저장은 업무 상태 변경과 분리한다. 결과 연결의 기존 완료/보류/취소 규칙과 Flow·휴지통 제외 정책을 회귀 검증한다. 신규/복원 경로를 갖춘 뒤 목록 조회의 전체 대조를 제거한다.

## 7. 재시도와 동시 실행

- 동일 이벤트는 같은 ID·같은 payload로 재시도한다. 응답 유실은 수신/저장 영수증부터 확인한다.
- 네트워크 일시 오류·BUSY만 제한 재시도하고 지연 분산을 적용한다. 권한·데이터 오류는 무한 반복하지 않는다.
- 서버 배치 작업의 진행 위치와 실패 대상을 보관한다. 화면에서 Promise를 기다리지 않게 하는 것만으로 서버 작업화됐다고 판단하지 않는다.
- 백그라운드 대기열 처리의 중복 실행 제어가 필요하면 작업 lease를 별도로 두고 만료·갱신·실행자 교체·늦은 완료 거부를 지원한다. 관리자 편집에는 이 lease를 적용하지 않는다.
- 검수 저장은 본문 버전 CAS로 확정한다. 댓글·담당자·PDF의 무관한 변경으로 발생한 접수 키 CAS 경합은 관련 데이터를 보존하며 제한 재시도한다. 본문·권한·연결·삭제 상태 변경만 사용자 재확인 대상으로 구분한다.
- 공유 조회는 확정된 본문 버전만 읽는다. 관리자 초안이나 준비 중 필드를 먼저 공개하지 않는다. GAS 미러는 반영 버전을 별도 추적하므로 앱 저장과 동시 반영됐다고 표시하지 않는다.
- 검수/문서의 증가하는 버전과 원본의 식별용 해시는 구분한다. 현재 원본 version은 해시이므로 문자열 크기로 신구를 판단하지 않는다. 새 이벤트에는 스키마 세대와 서버가 검증하는 순서를 두고 이전 이벤트가 최신 데이터를 덮지 못하게 한다.
- `hwSource_()`의 원본 해시는 현재 PDF도 포함한다. 새 본문 해시에서는 PDF/수신 메타데이터를 제외하고 기존 해시와 schemaVersion으로 구분한다. PDF 등록만으로 본문 수신 오류나 검수 충돌이 생기지 않아야 한다.
- 스냅샷 전송에서도 삭제·휴지통·대상 연결 검증을 유지한다. 삭제된 원본을 지연 이벤트가 복원하지 못하게 한다.
- 개별 중복 ID·잘못된 데이터는 대상 오류로 격리하고 정상 항목은 진행한다. 전체 저장소 읽기 실패는 체크포인트를 유지하고 중단한다.

## 8. 관측과 상태 표시

작업 ID, 이벤트 종류, 범위, 단계, 시도 횟수, 구조화된 오류 코드와 소요 시간을 기록한다.

측정값: `lockWaitMs`, `lockHeldMs`, `sourceReadMs`, `queueWriteMs`, `gasMs`, `ingestMs`, `reviewSaveMs`, `reconcileMs`, `listMs`, `totalMs`, 처리/스캔 건수, 응답 바이트.

로그에는 토큰·서명·병원명·댓글·원본 본문·사진 URL을 기록하지 않는다. GAS 잠금의 직접 획득 결과를 분류하고 번역된 예외 문구 문자열에만 의존하지 않는다.

`BUSY`, `UPSTREAM_TIMEOUT`, `SOURCE_INVALID`, `SOURCE_MISSING`, `INGEST_FAILED`, `REVIEW_CONFLICT`, `REVISION_INVALID`, `AUTH_REQUIRED` 등을 구분한다. 일반 사용자에게는 의미 있는 안내를, 관리자 진단에는 단계·오류 코드를 제공한다.

목록 조회 성공, 원본 수신 성공, 검수 저장 성공, 보고 반영 성공, PDF 저장/첨부 성공을 구분한다. 원본 장애를 전체 목록 실패로 표시하지 않는다. 앱 검수 저장 성공 뒤 보고 반영 실패를 저장 실패로 바꾸지 않는다.

구조적 완료 기준은 목록 조회의 GAS 호출·자동 연결 실행 0회, 저장 잠금 안 외부 통신 0회, 앱 편집 잠금/점유 API 0개다. 성능 개선률과 지연 목표는 운영 기준치를 측정한 후 정하며 현재 확정 수치로 약속하지 않는다.

## 9. 배포·전환·롤백

1. 실제 GAS 배포 버전·시간 트리거·데이터 소비자를 확인한다.
2. 원본/검수/문서 경계를 지원하는 호환 서버와 저장 스키마·검사부터 준비한다.
3. GAS 저장 잠금·수신 이벤트·검수본 반영 경로를 배포하고 실제 시간 작업을 확인한다.
4. Deno 기능을 활성화하고 기존 수정모드·PDF 독립 경로·프런트/SW를 의존성에 맞게 적용한다.
5. 관리자와 다른 권한 계정의 조회, 시트/보고서 반영, 구버전 캐시 경로를 확인한다.

기존 유효한 정정본과 이전 대기 이벤트를 기준으로 전환 세대/기준 버전을 확정한다. 과거 최초 원본이 없으면 이전 연동 기준본으로 명시하고 추정 복원하지 않는다. 정상 전환 전 이벤트를 새 정책 위반으로 일괄 격리하지 않는다.

기존 데이터 초기화·원본 일괄 덮어쓰기·대기열 삭제·전체 재이전을 하지 않는다. 구버전 API가 새 검수본을 원본으로 덮어쓰지 못하도록 서버에서 통제한다. 이전 연동본에 검수자·검수 시각을 소급 생성하지 않는다.

롤백은 기능 플래그와 호환 코드로 수행한다. 미처리 검수 이벤트는 보존하고 처리 가능한 서버 코드를 제거하지 않는다. 앱 화면을 되돌린다는 이유로 예전 자동 원본 수신이 검수본을 덮어쓰게 만들지 않는다.

## 10. 검증과 관련 코드

주 계획서의 업무 시나리오 외에 다음을 검증한다.

- 원본 서버 장애·장시간 잠금 중에도 목록 조회 가능
- 변경 0건에서 접수 100/1,000/10,000건의 불필요한 전체 매칭 스캔 없음
- 변경분 중간 실패·잘못된 revision·커서 정지 복구
- 저장 잠금 안 외부 통신 0회와 ID/대기열 무결성
- 신규 접수·수정·복원과 원본 선도착의 매칭
- 동시 작업·중단·부분 전송·응답 유실의 재개와 중복 방지
- 지정 관리자 외의 저장 후 본문 수정 차단, 최초 저장 재시도와 중복 신규 작성 구분

- 같은 관리자 두 창/기기 버전 충돌, 댓글/PDF의 무관한 변경 보존
- 원본·보고서 이벤트 순환과 검수본 덮어쓰기 차단
- PDF 현장 즉시 처리 및 원본 변경 후 파일 해시 불변
