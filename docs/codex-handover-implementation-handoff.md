## 3. 다시 결정할 필요 없는 합의

- 수정자는 지정된 관리자 1명, 사용자 본인이다. 등급만 보고 여러 계정에 수정 권한을 열지 않는다.
- 현장 사용자는 신규 작성·최초 저장을 한다. 저장된 본문 정정은 관리자만 앱에서 수행한다.
- 기존 수정모드와 접수 상세를 확장한다. 별도 검수 앱이나 GAS 수동 전송 버튼을 만들지 않는다.
- ✓는 로컬 입력 적용, Handover 저장은 Deno 확정·공유다.
- 편집 잠금·점유 예약·heartbeat·만료/강제 해제 기능은 없다.
- 편집 중에는 기존 저장본을 제공한다. 서버의 원자적 확정 후 새 저장본을 제공한다. 응답이 늦더라도 이미 확정된 새 데이터는 다른 사용자가 조회할 수 있다.
- 동일 관리자 두 창/기기의 저장 충돌은 본문 버전 검사로 방지한다. 같은 저장 재시도는 동일 operationId·payload를 사용한다.
- 댓글·담당자·PDF 변경 때문에 본문 검수 충돌이 발생하지 않도록 버전을 구분한다.
- 원본과 검수본·감사 이력은 보존한다. 기존 원본 재전송은 검수본을 덮지 못한다.
- PDF는 현장에서 즉시 생성·저장·공유·첨부한다. 생성 당시 내용으로 고정하고 검수 대기·자동 재생성·원본 차이 경고를 요구하지 않는다.
- 목록 동기화는 GAS 원본 대조에 의존하지 않는다. GAS 내부의 필수 짧은 저장 잠금은 유지하고 잠금 안 외부 통신을 제거한다.
- GAS/보고서 반영은 비동기다. 앱 저장 성공과 시트 반영 완료를 구분한다.

## 4. 최종 검수에서 보완한 핵심

| 검수 항목 | 확인한 코드/설계 문제 | 구현 요구 |
|---|---|---|
| 관리자 계정 식별 | `verifyToken()`은 uid를 반환하지만 Work Actor에는 전달하지 않음 | 인증된 uid 전달·서버 지정 계정 검증. uid/설정 누락은 검수 저장 거절 |
| PDF와 본문 버전 | GAS `hwSource_()`가 pdf를 넣은 후 version 해시 계산 | 본문 해시에서 문서/전송 메타데이터 제외, 구/신 스키마 버전 구분 |
| 저장 완료의 의미 | 클라이언트 응답 대기와 서버 확정 시점을 혼동하기 쉬움 | 공개 전환은 서버 commit 기준. 응답 유실 시 영수증 확인 |
| 전송 스냅샷 | 기존 `hwKvDeliverSources_()`가 저장된 이벤트 대신 현재 원본 재조회 | 이벤트와 payload 일치 보장. 기존 삭제/휴지통 재검증 유지 |
| 기존 데이터 전환 | 이미 정상 정정된 기존 기록과 미처리 이벤트 존재 가능 | 유효한 기준본과 전환 세대 확정. 최초 과거값 추정 복원/대기열 일괄 폐기 금지 |
| 조회 부수 효과 | `work_sync`가 전체 `reconcileSources()` 실행 | 신규 접수·조건 수정·복원·원본 수신의 내구성 있는 후속 처리부터 마련 |
| 기존 저장 공통 함수 | `mutate()`는 접수 객체·전역 seq·감사·outbox와 결합, 48,000바이트 제한 존재 | 검수 payload/감사/영수증 크기 및 CAS 범위 점검. 현재 함수 단순 재사용으로 완료 처리하지 않음 |
| 전체 기능 범위 | 앱 편집만 구현하면 보고서는 원본을 계속 읽을 수 있음 | GAS 공통 조회 및 실제 대시보드·보고서 소비 경로까지 검증 |

본문 버전용 해시는 식별값이며 대소 비교로 최신 순서를 판정하지 않는다. 검수 버전·문서 버전·목록 seq·원본 스키마 세대를 구분한다.

## 5. 구현 순서와 단계별 종료 조건

### 단계 0 — 작업 기준 확보

- 최신 main과 기준 SHA를 비교하고 관련 변경을 먼저 확인한다. 이 계획을 오래된 코드에 무조건 적용하지 않는다.
- 기존 AGENTS.md가 새로 추가됐으면 읽는다. 검수 시점 저장소에는 없었다.
- 아래 기준선 검사와 인증 uid 전달 경로를 확인한다.
- 실제 운영 로그·GAS 배포·트리거·관리자 uid는 이 작업에서 확인되지 않았다. 운영 값이 없어도 로컬 fixture로 구현·검증은 진행한다. 값을 임의 추정하지 않는다.
- 실제 필드 매핑과 소비 경로를 작성한다. 접수 미연결 Handover가 기존 수정모드에 노출되는지 확인하고, 접근 경로가 없으면 해당 누락을 명시한다. 임의 접수를 만들어 연결하지 않는다.

### 단계 1 — 공통 안정화

- 일반 동기화의 `work_handover_refresh` 선행 조건을 제거한다.
- 원본 수신·접수 생성/수정/복원 후 대상 매칭을 내구성 있는 작업으로 예약하고 실제 처리기/재시도 실행 경로를 연결한다. 대기 항목만 만들어 두고 처리기를 누락하지 않는다.
- 위 경로를 검증한 뒤 목록 조회의 전체 reconcile을 제거한다.
- GAS 잠금 안 외부 통신·대기열 반복 스캔을 줄인다. ID 생성·기존 삭제 보호·원본 저장과 이벤트의 복구 가능성은 유지한다.
- 완료: GAS 장애 중 목록 정상, 변경 0건에서 전체 매칭 없음, 새 접수/복원/원본 선도착의 자동 연결 유지.

### 단계 2 — 서버 저장과 데이터 경계

- 인증된 uid 전달, 지정 관리자 설정, 검수 API와 본문/문서 스키마 분리를 구현한다.
- 최초 저장본과 검수본을 분리하고 모든 legacy 수신·알림·PDF 경로의 덮어쓰기를 차단한다.
- 검수본·감사·변경분·반영 이벤트·작업 영수증을 일관되게 확정한다.
- 본문 CAS와 동일 작업 재시도를 구현한다. 다른 필드의 변경은 보존하고 불필요한 충돌을 줄인다.
- 완료: 미지정 계정 거절, 원본/PDF 재전송 보호, 두 창 충돌, 응답 유실 복구, 크기 상한 처리 통과.

### 단계 3 — 기존 화면 확장

- 기존 수정모드에서 recordId별 본문을 편집한다. 접수 저장과 Handover 저장의 대상을 구분한다.
- 미저장 표시·실패 시 입력 유지·수정 없는 최초 검수 완료·충돌 비교를 구현한다.
- 편집 시작 시 최신 조회. 저장 중 입력 처리 방식과 제출 payload를 고정한다. 늦은 응답으로 초안을 지우지 않는다.
- 완료: 편집 중 일반 계정은 기존본, 서버 commit 후 최신 조회는 새 본문 전체를 확인. 입력/조회에 서버 편집 잠금 없음.

### 단계 4 — PDF 독립화

- 원본 최신 지문 불일치 차단·재생성 경고를 제거하고 문서 등록/연결을 독립시킨다.
- 생성 시 실제 입력·수동 입력·사진·서명 보존. 이미 생성한 파일은 그대로 재시도한다.
- 완료: 검수 전에 현장 PDF 사용 가능, PDF 등록으로 본문 버전 변화 없음, 검수 전후 파일 해시 불변, 정확한 접수 첨부.

### 단계 5 — GAS/보고서 반영

- 검수본 별도 저장소·버전별 반영·공통 조회 계층을 구현한다.
- 실제 소비 함수마다 검수본 우선/기존본 fallback, 중복 집계 방지, 실패 상태를 검증한다.
- 완료: 앱과 GAS/보고서의 적용 버전 일치, 순서 역전/재시도/중단 복구, 순환 수신 없음.

### 단계 6 — PR·배포 준비

- 의미 있는 단계 단위로 PR을 준비하되, 중간 단계만으로 전체 완료라고 표시하지 않는다.
- 코드·검사·설정 예시·활성화 순서·롤백 절차를 함께 제공한다. 설정 예시에 실제 uid·토큰·비밀값을 넣지 않는다.
- 기존 `.github/workflows/static.yml`은 main push 시 Pages 배포를 실행한다. 준비/구현 브랜치에서 작업하고 main 병합·workflow_dispatch를 임의 실행하지 않는다.
- 운영 활성화 전 PDF 독립화·서버 호환·구버전 SW·GAS 실제 배포·트리거를 확인한다.
