# 휴대폰 검색·PDF 검증

운영 반영 전 Android Chrome/설치 앱과 iPhone Safari/홈 화면 앱에서 확인한다. 자동 검증은 브라우저 엔진·기기 메모리·백그라운드 종료·실제 Google 전송 시간을 대신하지 않는다.

## PDF 후보 변경

- 도구·글꼴 준비 → AS 처리 현황 연결 확인 → 본문·서명 생성 → 사진·파일 생성의 현재 단계를 표시한다. 실패한 단계의 시간도 `BazPerf.report()`에 남긴다. 병원명·사진·서명·토큰은 성능 기록에 넣지 않는다.
- PDF 도구 다운로드와 이미지 준비는 30초, 글꼴 준비는 15초에 안내 오류로 종료한다. 사진 기본 처리의 이미지 읽기·압축·파일 읽기도 각 30초에 정리한다. 성공한 이벤트에 추가 지연을 넣지 않는다.
- AS 처리 현황 확인은 30초, Drive 업로드는 기존 120초의 응답 제한을 쓴다. 이는 예상 소요 시간이 아니라 무한 대기 방지 기준이다. 앱이 백그라운드에 있으면 타이머 실행 자체가 지연될 수 있다.
- 일시적인 연결 실패·응답 유실·5xx/429 오류로 사전 확인에 실패했으면, 생성된 파일을 유지하고 같은 병원·일자·S/N·기록 ID로 확인과 저장을 다시 시도한다. 파일 읽기가 실패해도 재생성 없이 읽기를 다시 시도한다.
- 권한 오류·일치 기록 없음·기록 ID 불일치·문서 버전 충돌은 자동으로 우회하지 않는다. 생성 당시 계정이 바뀌면 전송을 중단한다. 토큰은 모듈 내부 메모리로만 연결하고 작업 데이터에 추가하지 않는다.
- 한 번 확정한 문서 버전과 전송 식별자·해시·파일은 재시도에서도 유지한다. 저장이 끝났으면 댓글 확인만 재시도한다.
- Android의 정상 Worker 경로, 최대 사진 치수 1600px, JPEG 품질 .8, PDF 크기 초과 시 .8/.72 재압축, 사진별 비율, 기존 파일 공유 동작은 유지한다.

본문 전체를 캡처하는 방식과 미리보기의 비동기 새 창, Google 로그인 흐름은 이 후보에서 변경하지 않는다. 큰 본문의 메모리 한계·Safari 로그인/새 창·앱 전환 중 중단은 추가 실기기 확인 대상이다. AS 처리 현황 본문 수정은 문서 스냅샷을 무효화하지 않는 기존 정책을 유지하며, 파일 버전 충돌 검사는 별도로 유지한다.

## 자동 검증

`inspection-upload.mjs`, `inspection-pdf-recovery.mjs`, `inspection-performance.mjs`, `inspection-photo-layout.mjs`, `inspection-pdf-formats.mjs`, `inspection-pdf-filenames.mjs`, `inspection-share-ui.mjs`, `inspection-upload-gas.mjs`, `work-document-flow.mjs`.

합성 PDF/사진과 가상 서버 응답만 사용한다. 운영 접수·AS 처리 현황·Drive·댓글에는 시험 데이터를 쓰지 않는다.

## 실기기 확인표

| 대상 | 검색 입력 중 선택·키보드·스크롤 | 사진 선택·방향·PDF 생성 | 파일 공유·취소·재시도 | 로그인·설치 앱 | 결과 |
|---|---|---|---|---|---|
| Android Chrome | 대기 | 대기 | 대기 | 대기 | 미확인 |
| Android 설치 앱 | 대기 | 대기 | 대기 | 대기 | 미확인 |
| iPhone Safari | 대기 | 대기 | 대기 | 대기 | 미확인 |
| iPhone 홈 화면 앱 | 대기 | 대기 | 대기 | 대기 | 미확인 |

사진 없음, 세로·가로 사진 혼합, 현장 사진 여러 장, 한글 서명, 표준·간소화 양식을 확인한다. 같은 사진으로 생성 단계별 시간과 최종 용량을 기록한다. 별도 로컬 생성 확인 화면은 실제 Google 저장·댓글 전파 속도를 측정하지 않는다. 운영 전송 검증은 권한 있는 사용자가 실제 필요한 문서를 처리할 때 저장 링크·연결된 원본·댓글을 확인한다.

검색 후보는 PR #253에서 별도로 검토한다. Android·iPhone 확인 전에는 운영 검색이나 PDF 모듈을 교체하지 않는다.
