# 기존 앱 수정모드 기반 Handover 검수·저장·공유 최종 계획서

수정일: 2026-10-15 (한국시간)  
선택된 방향: 관리자 1명이 기존 CS 서비스 현황의 수정모드에서 Handover를 검수·저장한다. 편집 잠금 없이 저장 완료된 데이터만 공유한다.  
검토 기준: main `f4429af2b143ed0ab83f10c790d731bb02ddd5f8` / PR #246  
상태: 최종 검수 완료된 구현 계획. 계획 문서만 별도 작업 브랜치에 준비하며, 애플리케이션 기능 변경·운영 데이터 변경·배포는 수행하지 않는다.

다음 작업 시작: [Codex 구현 인계서](codex-handover-implementation-handoff.md). 2026-10-16 작업 시 이 문서와 기술 부속 문서를 함께 읽는다.

## 1. 확정된 범위

1. 별도 검수 앱을 만들지 않고 기존 수정모드와 접수 상세를 확장한다.
2. Handover 수정·검수는 지정된 관리자 1명(사용자 본인)만 수행한다. 현장 사용자는 신규 작성과 최초 저장을 하고, 최초 저장이 완료된 본문은 수정하지 않는다. 입력 적용(✓)과 서버 저장을 구분한다.
3. 저장 성공 시 검수본·버전·수정자·시각·변경 이력을 Deno에 함께 확정한다. 별도의 GAS 전송 버튼이나 추가 공유 승인을 요구하지 않는다.
4. 관리자 수정 중에는 다른 사용자에게 기존 저장본을 제공한다. 저장 성공 시 수정 내용 전체를 한 번에 확정하고 다음 정상 조회부터 새 저장본을 제공한다. 저장 전 입력은 공유하지 않는다.
5. 현장 작성본과 관리자 검수본을 구분해 보존한다. 늦은 원본 수신이 검수본을 덮어쓰지 못하게 한다.
6. PDF는 현장에서 즉시 생성·Drive 저장·공유·댓글 첨부한다. 생성 당시 입력값·사진·서명으로 고정하고 관리자 검수나 이후 Handover 정정을 반영하지 않는다.
7. 목록 조회와 원본 수신·자동 연결을 분리하고 GAS 잠금 점유를 줄이는 안정화 작업을 함께 진행한다.
8. GAS와 기존 대시보드·주간/월간 보고서에도 같은 검수본을 적용한다. 반영은 앱 저장과 분리하고 지연·실패를 표시한다.
9. 편집 잠금·점유 표시·잠금 유효기간·다중 관리자 협업 기능은 도입하지 않는다. 같은 관리자의 두 창/기기에서 발생하는 덮어쓰기는 저장 순간의 원자적 버전 검증으로 방지한다. GAS 내부의 짧은 데이터 저장 잠금은 별도로 유지·축소한다.

이 문서를 최종 업무 설계 기준으로 사용한다. [동기화·잠금 안정화 실행계획](sync-separation-plan.md)은 이 설계의 기술 부속 문서다. 시트에서 검수한 뒤 수동 전송하는 이전 대안은 구현 대상에서 제외했다.

## 2. 현재 기능과 추가 개발의 경계

| 구분 | 현재 확인한 상태 | 추가할 기능 |
|---|---|---|
| 기존 수정모드 | 접수 정보 편집과 서버 저장 지원 | Handover 기록별 처리 본문 편집 |
| 처리 결과 저장 | 저장된 원본 선택·연결, 보완 메모 저장 | 관리자 정정본 저장·버전·검수 표시 |
| 공유 데이터 | Deno의 접수·이력 저장과 변경분 조회 | 미검수 원본과 공유 검수본 구분 |
| 변경 이력 | 기존 KV 트랜잭션·감사·멱등 처리 | Handover 필드별 변경 전후·검수 기준 버전 |
| 원본 수신 | GAS의 현재 원본 재조회·자동 연결 | 저장된 작성본의 내구성 있는 수신, 검수본 보호 |
| PDF | 원본 연결·최신 지문 비교와 의존 관계 존재 | 승인과 무관한 문서 저장·첨부, 자동 최신 비교 제거 |

기존 `work_result_save`는 Handover 본문 전체를 수정하는 API가 아니다. 기존 화면에 입력칸만 추가하는 것으로 서버 검수 기능이 완성되지 않는다.

## 3. 사용자 흐름

### 3.1 현장 사용자

- 기존 양식에서 현장 처리 기록을 신규 작성한다. 최초 저장 전에는 입력을 수정할 수 있다.
- 최초 저장 완료 후 본문 정정은 관리자에게 요청한다. 일반 사용자의 기존 기록 수정은 화면과 서버 양쪽에서 제한한다. 최초 저장의 중복 요청은 같은 작성 작업 ID로 복구하고, 이미 존재하는 recordId를 신규 작성 API로 덮어쓰지 못하게 한다.
- 저장이 확정된 원본을 검수 대기 데이터로 Deno에 전달한다. 전송이 지연돼도 이미 성공한 원본 저장을 실패로 바꾸지 않는다.
- PDF를 즉시 작성·저장·공유한다. 관리자 검수 여부를 생성 조건으로 사용하지 않는다.
- 이후 앱에서 검수본과 수정 이력을 권한에 맞게 확인한다.

### 3.2 관리자

1. 기존 CS 서비스 현황에서 접수 상세를 연다.
2. 연결된 Handover 기록을 선택하고 최신 저장본과 버전을 조회한 뒤 수정모드를 활성화한다. 서버에 편집 점유를 등록하거나 GAS 잠금을 획득하지 않는다.
3. 현재 공유본 또는 최초 작성본을 기준으로 필드를 수정한다. 원래 현장 작성본과 차이를 확인할 수 있다.
4. ✓는 현재 입력에만 적용한다. 서버 저장 전까지 다른 사용자의 공유본은 바뀌지 않는다.
5. 해당 기록의 `Handover 저장`을 실행한다. 이 버튼은 검수본을 서버에 확정하고 공유하는 동작임을 표시한다. 내용 정정이 필요 없으면 수정 없이 최초 검수 완료로 저장할 수 있다.
6. 정상 응답 후 검수자·검수 시각·버전을 표시한다. GAS/보고서 반영 대기가 있으면 별도 상태로 보여준다.

편집한 기록에는 `저장 전 변경`을 표시한다. 기록 전환·수정모드 해제·화면 이탈 시 미저장 입력을 확인하고, 저장 실패 시 입력을 유지한다. 통신 응답 유실은 `저장 결과 확인 중`으로 표시해 같은 작업 ID의 결과를 확인한다.

기존 접수 저장과 Handover 저장은 저장 대상이 다르므로 표시를 구분한다. 한 접수에 여러 장비·처리 기록이 있으면 불변 recordId별로 저장하며, 다른 기록이나 댓글을 함께 덮어쓰지 않는다. 대량 검수 편집은 초기 필수 범위에 넣지 않는다.

### 3.3 다른 사용자

관리자 편집 여부와 무관하게 기존 목록 동기화 또는 상세 최신 조회 시 마지막으로 저장 완료된 데이터를 받는다. 검수본이 없으면 최초 저장본을 미검수 상태로 제공한다. 편집 도중의 필드와 저장된 필드를 섞어서 응답하지 않는다. 자동 변경 알림을 제공하더라도 입력 중인 댓글·접수·검수 초안은 덮어쓰지 않는다. 저장 즉시 모든 열린 PC가 자동 갱신됐다고 표시하지 않는다.

## 4. 데이터 기준과 상태

| 데이터 | 기준과 보존 원칙 |
|---|---|
| 현장 작성본 | 최초 저장이 확정된 스냅샷 보존. 불변 recordId·작성자·작성 시각 유지. 일반 사용자 재수정 제한 |
| 편집 중 초안 | 관리자 브라우저의 계정·기록별 입력 상태로 관리. 공유 API·시트에 편집 내용을 중간 반영하지 않음 |
| 관리자 검수본 | Deno에서 확정한 공식 처리 내용. 검수자·시각·검수 버전·기준 작성 버전 포함 |
| 변경 이력 | 수정 전후·변경 필드·작업자·시각·동작 ID 보존 |
| PDF | 생성 당시 파일·입력 기준·생성자·시각·파일 해시·문서 버전 보존 |
| GAS 반영본 | 검수본의 반영용 복제. 적용한 검수 버전과 반영 시각 추적 |

새 기록은 검수본이 없으면 최초 저장본을 `미검수`로 표시한다. 검수 저장 후에는 마지막 저장이 완료된 검수본을 기본 표시한다. 관리자 재편집 중에도 이 검수본을 유지하고 다음 저장 성공 후 전체 내용을 교체한다.

현장의 저장 후 본문 재수정은 정상 업무 흐름에 두지 않는다. 오래된 클라이언트·직접 시트 편집·이전 대기열에서 다른 원본이 들어오면 공유본을 덮지 않고 관리자 복구 대상으로 격리한다. 이 예외를 일반 재검수·양방향 편집 체계로 확장하지 않는다.

| 시점 | 관리자 화면 | 다른 사용자 및 공유 조회 |
|---|---|---|
| 수정 전 | 현재 저장본 | 현재 저장본 |
| 수정 중·✓ 적용 후 | 관리자 초안 | 기존 저장본 |
| 서버 확정 전 | 입력 보존·진행 표시 | 기존 저장본 |
| 서버 확정 후·응답 도착 전 | 저장 결과 확인 중일 수 있음 | 최신 서버 조회는 새 저장본 |
| 서버 저장 실패/충돌 | 입력 보존·오류/비교 표시 | 마지막 확정본 유지 |
| 응답 유실 | 입력 보존·저장 결과 확인 | 서버 확정 여부에 따른 마지막 확정본 |
| 저장 성공 | 새 저장본·버전 | 다음 정상 조회부터 새 저장본 |

검수 상태와 A/S 업무 상태는 별개다. 검수 저장만으로 접수·방문예정·처리중·결과확인·완료·보류·취소 상태를 변경하지 않는다. 기존 완료 시각·완료자·담당자·예정 방문·접수 증상·보완 메모·댓글은 검수 대상 필드가 아닌 한 보존한다. 기존 결과 연결/업무 상태 변경 기능과 검수 저장을 별도 동작으로 구현한다.

목록 표시는 `미검수`, `검수 완료`, `시트 반영 대기`를 구분한다. `저장 전 변경`은 관리자 화면의 로컬 상태다. 편집 여부를 공유 상태로 기록하거나 편집 잠금을 만들지 않는다. 비정상 원본 변경은 일반 상태와 분리해 관리자에게만 복구 필요로 표시한다.

## 5. 편집 범위와 권한

| 필드 | 처리 원칙 |
|---|---|
| 처리 내용·처리 결과·특이사항 | 관리자 본문 수정 지원 |
| A/S·점검 구분, 분류·유형 | 기존 값·마스터와 정합성 검증 |
| 교체품·비용 | 기존 데이터 형식·허용 범위 검증 |
| NS 평가·노즐 재사용 등 | 실제 원본 스키마와 현재 입력 규칙에 맞춰 편집 |
| 병원·처리일·S/N·실제 처리자 | 식별·책임 정보 변경을 확인하고 감사 기록. 접수 연결을 자동으로 다른 병원으로 옮기지 않음 |
| 불변 기록 ID·원작성자·원작성 시각 | 읽기 전용. 검수자·시각은 별도 저장 |
| PDF·사진·서명 원본 | 본문 검수로 변경하지 않음 |

본문 검수 저장 권한은 서버에서 인증된 사용자와 지정 관리자 1명의 계정 식별자가 일치하는지 검증한다. 기존 인증의 관리자 조건도 함께 적용하며, 단순 관리자 등급 전체나 클라이언트의 버튼 표시·표시 이름·cachedLevel만 신뢰하지 않는다. 식별자는 기존 인증이 보장하는 값과 서버 설정으로 정하고 화면에서 임의 지정하지 않는다. 현재 `verifyToken()`은 uid를 반환하지만 `workForward()`가 업무 저장소로 넘기는 Actor에는 uid가 없다. 해당 전달 경로와 Actor 타입을 먼저 확장한다. 지정 uid 설정이 없거나 uid 없는 구형 토큰이면 검수 저장을 거절하고 재로그인을 안내한다. 일반 조회·신규 작성의 기존 호환성은 별도로 유지한다. 실제 관리자 uid는 운영 인증에서 확인하며 이름으로 추정하거나 저장소에 하드코딩하지 않는다.

신규 작성 권한과 저장된 본문 수정 권한을 구분한다. 최초 저장 작업의 재시도는 같은 작업 ID·같은 내용으로만 허용하고, 기존 recordId에는 신규 생성 전용 조건을 적용한다. 일반 사용자가 기존 저장·수정 API나 GAS 경로로 기존 본문을 바꾸지 못하게 한다. 관리자의 정상 본문 정정 경로는 앱 검수 저장으로 통일한다. 기존 접수 수정·작성자 댓글 편집 권한은 해당 기능의 기존 규칙을 유지한다. 원본·검수본의 열람 범위는 기존 업무 권한을 따른다.

## 6. 편집 잠금 없는 저장·공유

### 6.1 조회와 편집

수정모드 진입 시 최신 저장본과 본문 검수 버전을 조회한다. 이후 편집·✓ 적용은 관리자 브라우저의 초안만 바꾼다. 편집 잠금, 점유 예약, 편집 heartbeat, 편집 잠금 만료·해제 API를 만들지 않는다. 다른 사용자의 조회는 편집 중에도 정상 처리한다.

Handover 검수 전용 저장 동작을 추가한다. 저장 요청에는 recordId, 확인된 requestId, 기준 작성본 식별/버전, 기준 검수 버전, 수정 필드와 operationId를 포함한다. 서버는 지정 관리자 권한·대상 연결·삭제 상태·현재 본문 버전·필드 형식을 검증한다. 아래 명칭은 설계상 책임 구분이며 실제 API·키 이름은 기존 규칙에 맞춘다.

### 6.2 저장 순간의 원자적 확정

다음 항목을 하나의 KV 원자적 트랜잭션으로 확정한다.

1. 검수본 전체와 증가한 검수 버전
2. 수정 전후 감사 이력과 검수자·시각
3. 접수 상세/목록에 필요한 이력·요약 및 변경분 이벤트
4. GAS/보고서 반영 대기 이벤트
5. 같은 operationId의 결과를 복구할 수 있는 저장 영수증

조회는 이 확정이 끝나기 전 기존 저장본을, 확정 후 새 저장본을 읽는다. 명시적인 최신 상세 조회와 저장 결과 확인은 강한 일관성 읽기 또는 동등한 버전 검증으로 보장한다. 클라이언트 캐시는 정상 동기화 전까지 기존본을 표시할 수 있으며, 캐시 표시를 최신 서버 조회 완료로 취급하지 않는다. 미완성 검수 데이터를 공유 조회 키에 먼저 쓰지 않는다. 서로 다른 시점의 본문 필드를 조합하지 않는다. 트랜잭션 크기·건수 제한을 구현 전에 확인하고 필요하면 최소 필수 데이터와 버전 지정 후속 투영으로 나누되, 공유 본문의 확정 경계는 유지한다.

GAS 통신이나 시트 반영을 기다리며 저장을 열어 두지 않는다. 앱 저장 성공은 Deno 확정 성공을 뜻한다. GAS 소비자는 반영 완료 전에는 이전 반영본을 제공하고 반영 완료 후 새 버전을 제공한다. 시스템 간 동시 확정을 약속하지 않으며 적용 버전·대기 상태로 차이를 표시한다.

### 6.3 동일 관리자 두 창/기기의 충돌과 재시도

관리자는 1명이어도 두 창이나 PC·모바일이 같은 버전을 편집할 수 있다. 예를 들어 두 창이 버전 5를 열고 첫 창이 6으로 저장하면, 두 번째 창의 버전 5 저장은 원자적 버전 검사로 거절한다. 현재 입력을 보존하고 최신 저장본과 비교해 다시 저장한다. 최근 요청 우선 덮어쓰기나 자동 전체 병합을 하지 않는다. 복잡한 다중 관리자 협업·현장/검수본 3자 자동 병합은 초기 구현 범위에서 제외한다.

댓글·담당자·PDF 등록 등 본문과 무관한 변경은 사용자에게 검수 충돌로 표시하지 않는다. 동일 접수 키의 CAS 경합은 최신 관련 데이터를 다시 읽어 보존하며 제한 재시도한다. 본문 버전·대상 연결·삭제·권한 변경은 다시 검증한다. 본문 버전과 PDF 버전·전체 목록 seq를 혼용하지 않는다.

저장 버튼을 누른 시점의 payload를 고정한다. 저장 중 추가 입력을 허용하는 구현이라면 제출한 초안과 이후 입력을 구분하고, 응답이 이후 입력을 덮거나 전체 초안을 지우지 못하게 한다. 초기 구현은 해당 기록의 입력·중복 저장 버튼만 요청 처리 중 잠시 비활성화하는 방식으로 단순화할 수 있다. 이는 서버 편집 잠금이 아니며 다른 사용자의 조회를 막지 않는다.

동일 저장 요청은 같은 operationId와 같은 payload로 재시도한다. 응답 유실은 영수증을 확인하고 중복 검수·감사·반영 이벤트를 만들지 않는다. 같은 ID의 다른 payload는 거절한다. 수정 없이 최초 검수를 확정할 수 있고, 이미 같은 버전을 검수한 상태에서 변경 없이 반복 저장하면 불필요한 버전·알림을 만들지 않는다.

계정 변경·로그아웃 후 이전 요청의 응답을 현재 화면에 적용하지 않는다. 늦은 목록·상세 응답이 높은 본문 버전의 저장 결과나 편집 초안을 덮어쓰지 못하게 한다.

## 7. 현장 원본 수신과 자동 연결

앱 검수를 위해 현장 원본은 관리자 검수 전에 Deno로 들어와야 한다. 원본 수신은 검수본 확정과 다른 경로로 저장한다.

- 현장 저장이 확정된 시점의 불변 ID·작성 버전·스냅샷을 내구성 있는 이벤트에 기록한다. 시트 여러 셀의 부분 실패는 준비/확정 저널과 멱등 복구로 처리한다.
- 원본 저장 잠금 안에서는 이벤트 확정까지 수행하고, Deno 통신은 잠금 밖에서 실행한다. 전송 실패·응답 유실은 같은 이벤트를 재시도한다.
- 현재 전송기가 시트의 최신 행을 다시 읽는 동작은 수신 버전을 뒤섞지 않도록 조정한다. 전달한 버전과 내용이 일치해야 한다. 전송 직전 삭제/휴지통 여부와 연결 권한을 재확인하는 기존 보호는 유지한다. 스냅샷 전송으로 바꾼다는 이유로 삭제된 기록을 다시 살리지 않는다.
- 원본 재수신·수동 새로고침·알림 조회·PDF 업로드가 검수본을 갱신하는 API를 우회 호출하지 못하게 한다.
- 일반 사용자의 저장 후 본문 수정은 서버에서 차단한다. 직접 시트 편집 권한도 운영 정책에 맞춰 제한한다. 직접 편집·구버전 재저장 등 비정상 변경은 격리·진단하고 관리자가 앱에서 정정하도록 한다. 원본 재수신·지문 비교는 누락 복구 수단이며 검수본 덮어쓰기 수단이 아니다.
- 새 접수, 연결 조건 변경, 복원, 원본 수신은 필요한 대상만 자동 연결 대기열에 넣는다. 원본을 먼저 수신한 뒤 접수가 생기는 경우도 처리한다.
- 미검수 원본의 접수 연결과 관리자 검수 확정은 구분한다. 원본 도착만으로 관리자 검수 완료라고 표시하지 않는다. 기존 결과 연결/완료 규칙의 회귀 검증도 수행한다.

원본 연결은 불변 ID와 검증된 병원·처리일·장비 맥락을 따른다. 중복 ID·다중 후보·누락은 확인 필요로 남기고 임의 연결하지 않는다. 휴지통·영구 삭제·Flow 보존 이력의 기존 정책을 유지한다.

## 8. 목록 동기화와 잠금 안정화

상단 일반 동기화는 Deno의 목록 변경분만 조회한다. GAS 원본 확인, 전체 원본 대조, 전체 접수 자동 연결을 일반 조회에 포함하지 않는다. 검수 저장과 원본 수신은 각각 필요한 변경 이벤트를 만든다.

기존 `work_sync`의 전체 `reconcileSources()` 의존성을 제거하기 전에 원본 수신·신규 접수·연결 조건 수정·복원 경로의 후속 처리 대기열을 준비한다. 목록 조회의 부수 효과로만 연결되던 기록이 누락되지 않게 한다.

GAS 저장 잠금 안의 외부 서버 통신을 제거하고 조회·대기열 반복 스캔을 축소한다. ID 할당·필수 시트 갱신은 짧은 잠금 안에서 대상과 버전을 다시 확인한다. 조회용 잠금 대기와 실제 저장 잠금 정책은 구분한다.

일반 사용자에게 별도 전체 Handover 원본 대조 버튼을 주 작업으로 요구하지 않는다. 관리자 복구용 원본 재수신·대기열 재시도는 분리된 관리 기능이며 검수본을 직접 덮어쓰지 않는다. 세부 구현은 기술 부속 문서를 따른다.

## 9. PDF 독립 처리 — 사용자 확정 조건

1. 현장 처리 직후 실제 양식의 최종 입력값·사진·서명을 캡처해 PDF를 생성한다. Handover에 없는 수동 입력도 생성 당시 문서 내용에 포함한다.
2. 생성·Drive 저장·공유·올바른 접수 댓글 첨부는 관리자 검수·검수본 존재 여부와 무관하게 가능해야 한다.
3. 생성 뒤 Handover 원본 수정·검수 저장·목록 동기화가 기존 PDF의 내용·해시·사진·서명·생성 시각을 변경하지 않는다.
4. Handover 최신 값과 비교하는 ‘원본 변경·PDF 재생성 필요’ 자동 비교·경고는 제거한다. 검수 이후 차이가 있어도 PDF를 오류로 표시하지 않는다.
5. 생성·업로드 사이 원본이 바뀌었다는 이유만으로 이미 생성한 파일의 저장·첨부를 막지 않는다. 생성 당시 문서 데이터로 저장한다.
6. 사용자가 명시적으로 재생성하면 그 시점의 입력으로 새 문서 버전을 만든다. 기존 문서 이력은 보존한다.
7. 파일 무결성·권한·기록/접수 연결·동시 문서 등록·중복 업로드 검증은 유지한다.
8. 현재 `hwSource_()`는 PDF 정보를 포함한 뒤 원본 version을 계산한다. 본문 검수용 버전/해시에서 PDF 메타데이터·수신 시각을 제외하고 문서 버전과 분리한다. PDF 등록만으로 비정상 본문 변경·검수 충돌이 발생하지 않게 한다. 기존 해시와 새 본문 해시는 schemaVersion으로 구분해 전환한다.

현재 원본 처리 이력이 먼저 연결돼 있어야 PDF를 첨부할 수 있는 의존성을 변경한다. 인증된 현장 저장 영수증·recordId·확인된 requestId로 문서 연결을 검증하고 문서 전용 등록부에 보관한다. PDF 전달을 위해 미검수 처리 본문을 검수본으로 수신하지 않는다.

접수 연결이 확인된 문서는 검수 전에도 바로 첨부한다. 접수 자체가 없는 독립 현장 문서는 생성·저장·공유를 허용하고 연결 가능해진 후 문서 ID로 첨부한다. 임의의 병원 접수에 추정 연결하지 않는다.

Drive 저장 성공·댓글 연결 실패는 파일을 다시 만들지 않고 같은 문서/전송 ID로 연결만 재시도한다. Handover 원본 수신·GAS 검수본 반영 이벤트에 오래된 PDF 메타데이터가 포함돼도 독립 문서 등록부를 덮어쓰지 못하게 한다.

## 10. GAS·대시보드·보고서 일관성

공식 검수본의 기준은 Deno다. GAS에는 원본을 보존하고 검수본을 별도 반영 저장소에 버전별로 저장한다. 기존 보고서가 원본을 직접 읽고 있으면 저장만으로 같은 값을 보게 된다고 가정하지 않는다.

구현 전에 아래 소비 경로를 조사해 공통 조회 계층에서 ‘검수본 우선, 검수본이 없으면 현장 작성본’ 원칙을 적용한다.

- CS 서비스 현황과 병원 처리 이력
- 대시보드 집계와 원인 분석
- 주간/월간 보고와 PPT·Excel 출력
- 검수 관련 변경 비교·열람 확인

불변 recordId와 검수 버전으로 반영하고, 먼저 처리한 이벤트는 반복 적용하지 않는다. 낮은 검수 버전으로 최신 반영본을 덮어쓰지 않는다. GAS 반영 성공을 확인한 이벤트만 전송 대기열에서 확정한다.

GAS 반영본을 신규 현장 작성본으로 다시 수신하는 순환을 막는다. 수동 시트 수정은 정규 검수 경로로 사용하지 않고 비정상 원본 변경으로 격리한다. 관리자 정정은 앱의 검수 저장으로 통일한다. 기존 원본행 자체를 다시 쓰는 방식이 불가피한 소비 경로는 별도 확인 후 원본 보존·버전 검증·충돌 처리를 포함해 설계하고, 그 의존성이 해결되기 전 해당 보고서를 검수본 적용 완료로 표시하지 않는다.

보고서 반영 실패는 ‘앱 저장 완료 / 시트 반영 대기’로 표시한다. 앱 검수 저장을 실패로 되돌리거나 관리자가 같은 검수 내용을 다시 입력하도록 요구하지 않는다.

| PDF 저장 성공·댓글 첨부 실패 | PDF 저장 완료 / 첨부 재시도 필요 |
| 로그인 만료 | 로그인 필요. 무한 자동 재시도 중단 |

기존 ‘변경 내용 확인’은 다른 사용자가 공유된 검수 정정본을 읽었는지 확인하는 기능으로 유지할 수 있다. 관리자 검수 저장의 두 번째 승인으로 사용하지 않는다. 알림 진입은 최신 접수/검수 버전과 해당 범위의 조회 성공을 검증한다. 매번 GAS 초안을 읽어 최신 확인 조건을 채우지 않는다.

목록 조회 시각, 원본 수신 시각, 검수 저장 시각, GAS/보고서 반영 시각을 구분한다. 한 시각으로 모든 데이터의 최신 상태를 대표하지 않는다. 일반 계정의 열람 권한은 기존 규칙을 따른다.

## 12. 단계별 구현과 완료 기준

| 단계 | 변경 내용 | 완료 기준 |
|---|---|---|
| 0. 현재 상태 확인 | 운영 GAS 버전·트리거·잠금 로그·기존 편집/보고 소비 경로 조사 | 추정과 실측 구분, 적용 대상 확정 |
| 1. 공통 안정화 | 목록/GAS 원본 분리, 잠금 안 통신 제거, 오류 단계 분류 | 원본 장애에도 목록 조회 가능, 잠금 안 외부 통신 0회 |
| 2. 원본·검수 데이터 경계 | 최초 저장본 수신, 검수본·감사·반영 대기 스키마, 지정 관리자 권한과 기존 수정 경로 차단 | 일반 사용자 재수정 불가, 원본 재수신이 검수본을 덮지 않음 |
| 3. 기존 수정모드 확장 | 잠금 없는 로컬 편집·입력 적용·변경 비교·원자적 저장 | 수정 중 기존본 조회, 저장 후 새 버전 조회, 두 창 충돌·응답 유실 복구 |
| 4. PDF 독립화 | 원본 최신 비교 제거, 문서 전용 저장·즉시 첨부 | 검수 전 사용 가능, 검수 후 기존 PDF 해시 불변 |
| 5. GAS·보고서 반영 | 반영 이벤트·검수본 조회 계층·소비자 적용 | 앱과 보고서 검수 버전 일치, 실패 재개 가능 |
| 6. 운영 전환 | 호환 서버·GAS 배포, 프런트/SW 적용, 제한 범위 검증 | 구버전 호환·누락/중복 없음·진단 가능 |

공통 안정화를 먼저 검증하고 검수 편집을 별도 활성화한다. 지정 관리자 1명과 조회용 일반 계정으로 제한 검증한 뒤 확대한다. PDF 독립화는 검수 기능의 운영 활성화 전에 검증한다. 단계 3만 끝나도 모든 기존 보고서와 PDF 의존성이 해결됐다고 보고하지 않는다. 사용자가 선택한 전체 동작의 완료 기준은 4~6단계 검증을 포함한다.

호환 서버 기능과 데이터 경계를 먼저 준비하고 GAS·Deno·프런트 기능을 의존성 순서대로 활성화한다. 저장소의 GAS 파일 수정만으로 실제 배포됐다고 판단하지 않는다. 시간 트리거의 실제 실행 코드도 확인한다. 새 클라이언트가 미배포 API에 의존하는 기간을 만들지 않는다.

전환 시 기존 기록은 이미 정상 정정된 내용이 있을 수 있으므로 최초 작성 당시 값으로 되돌리지 않는다. 현재 유효한 저장본을 이전 연동 기준본으로 보존하고, 진행 중인 기존 대기 이벤트와의 순서를 확인해 기준 버전을 정한다. 확보하지 못한 과거 최초 원본을 새로 만들어내지 않는다. 기준 확정 전의 정상 대기 이벤트를 신규 정책 위반으로 일괄 격리하지 않는다. 정책 활성화 시점/스키마 세대를 기록하고 그 이후의 일반 사용자 본문 변경을 차단한다.

기존 데이터·대기열은 삭제하거나 다시 이전하지 않는다. 기존 원본/연동본은 ‘이전 연동본’으로 유지하고 사용자가 검수했다고 소급 기록하지 않는다. 새 검수본 필드는 기존 기록을 읽을 수 있는 기본값과 호환성을 갖춘다. 미처리 반영 이벤트가 있는 동안 처리 가능한 서버 코드를 제거하지 않는다.

## 13. 필수 검증 시나리오

| 검증 | 기대 결과 |
|---|---|
| 기존 수정모드 활성화/해제 | 기존 접수 편집 정상, Handover 대상·권한 구분 |
| 처리 본문·유형·교체품·비용 수정 | 해당 recordId 검수본만 변경, 다른 장비·댓글 보존 |
| 일반 사용자·지정되지 않은 계정의 기존 기록 수정 API/GAS 호출 | 수정 거절. 신규 작성·정상 조회·PDF 작업은 해당 권한 유지 |
| ✓ 적용 후 화면 재표시/필터 변경 | 초안 유지, 공유 검수본 불변 |
| 관리자 편집 중·서버 확정 전 다른 계정 조회 | 기존 저장본 전체 제공, 중간 필드·초안 노출 없음 |
| 서버 확정 후 저장 응답 지연·유실 | 새 공유본 조회 가능, 재시도로 동일 저장 결과 복구 |
| PDF 메타데이터만 추가/변경 | 본문 버전 불변, 비정상 원본 변경으로 격리되지 않음 |
| uid 누락/미설정/지정되지 않은 관리자 계정 | 검수 저장 거절, 이름·등급만으로 우회 불가 |
| 기존 정상 정정본·미처리 대기열 전환 | 유효한 기존 내용 보존, 정상 이전 이벤트 누락 없음 |
| 정상 저장 후 다른 계정 조회 | 동일 새 검수 버전과 내용 표시 |
| 같은 관리자 두 창/기기에서 같은 버전 저장 | 뒤늦은 저장 충돌 검출, 입력 유지, 최신 검수본 보존 |
| 편집 중 댓글·담당자 변경·PDF 등록 | 본문 무관 변경 보존, 불필요한 검수 충돌 없음 |
| 수정 없는 최초 검수·변경 없는 반복 저장 | 최초 검수 확정 가능, 반복 버전/알림 생성 없음 |
| 응답 유실·중복 클릭 | 같은 operationId로 복구, 검수/감사/반영 중복 없음 |
| 원본 재전송·알림·구버전 원본 조회 | 관리자 검수본을 현장 원본으로 덮어쓰지 않음 |
| 원본보다 접수가 나중에 생성/복원 | 필요한 대상 매칭 재개, 임의 연결 없음 |
| 완료·보류·취소·휴지통·Flow | 업무 상태·완료 시각·보존 규칙 유지 |
| 편집모드 장시간 유지·창 종료 | 편집 잠금/예약 없음, 다른 사용자 조회·업무 영향 없음 |
| GAS 지연·잠금 점유·수신 실패 | 목록/검수본 조회 독립, 원본 전송 재개 |
| Deno 성공·GAS 실패·이벤트 순서 역전 | 반영 대기 표시, 낮은 검수 버전 적용 거부 |
| 병원명·처리일·S/N 정정 | 기록 식별 보존, 연결 이동은 명시적 확인 |
| PDF 검수 전 생성·저장·첨부 | 관리자 대기 없음, 정확한 접수 연결 |
| PDF 생성 중 원본 수정·이후 검수 | 생성 당시 파일 저장 가능, 이후 해시/내용 불변 |
| PDF 첨부 실패·재생성·동시 등록 | 동일 파일 재시도와 명시적 새 문서 버전 구분 |
| 기존 대시보드·주간/월간 보고 | 검수본 적용·집계 일관성 확인 |
| 계정 전환·로그아웃·구버전 SW | 다른 계정 응답 적용 없음, 호환 경로/복구 가능 |

관련 기존 검사를 재사용하고 권한·본문 편집·원본/검수본 분리·PDF 고정·보고서 투영에 필요한 검사를 추가한다. 단순 구현 모양을 확인하는 테스트 대신 실제 저장/공유/충돌 시나리오를 검증한다. 문서 수정만 수행한 현재 단계에서는 기능 검증이 완료됐다고 주장하지 않는다.
